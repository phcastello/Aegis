## Real build support and naming

Both supported builds embed existing foreground interactive audio: push-to-talk uses `getUserMedia`/`MediaRecorder` through `useAegisTranscription.ts`; TTS PCM playback uses WebAudio/AudioWorklet through `voicePlaybackService.ts`. Windows native permissions support microphone/autoplay; Android retains RECORD_AUDIO and its existing runtime permission flow.

The small Rust `CapabilityRegistry` therefore advertises `audio.input@1` and `audio.output@1` on Windows and Android. It describes implemented runtime support, not granted microphone permission, attached hardware, STT provider configuration, background reachability or remote command execution. Its isolated provider can omit unsupported input/output; no backend platform inference exists. Unsupported builds advertise nothing; no new platform support is added.

Backend catalog: exactly `audio.input`, `audio.output`. Name is case-sensitive `<domain>.<action>` (lowercase ASCII segments, digits allowed after first character); version is a positive Int32 integer per capability. No SemVer per capability and no future placeholders (`notification.show`, location, battery).

## Protocol and validation

Existing authenticated WSS endpoint `/api/nodes/connect`, header `Authorization: AegisNode …`, header `X-Aegis-Node-Protocol: 1`, hello/heartbeat/ACK lifecycle and shipped 25s heartbeat/75s timeout are unchanged. The native Rust task retrieves credentials; Vue receives only public metadata/state. No new WebSocket message types or command framework.

Hello protocol **v1** gets an optional field:

```json
{
  "protocolVersion": 1,
  "type": "hello",
  "messageId": "a UUID",
  "sentAt": "2026-10-03T18:00:00Z",
  "payload": {
    "appVersion": "0.7.0-stage.7",
    "capabilities": [
      { "name": "audio.input", "version": 1 },
      { "name": "audio.output", "version": 1 }
    ]
  }
}
```

Stage 04 clients sending only appVersion still connect. Omission means an empty capability set, including replacing previously stored metadata with empty on downgrade. Explicit null/non-array capability lists are rejected. Each item contains exactly name/version; malformed fields, invalid name/version, duplicates (identical or conflicting), more than 32 entries, or names over 64 characters reject hello with policy close 1008. Existing 4096-byte message/payload limits remain.

Valid unknown names are ignored for persistence/resolution, counted in a bounded log, and do not break known capabilities or the connection. They do not create authorization, endpoints, tools or commands. Accepted entries are sorted ordinally by name. Unknown/duplicate input still counts toward limits; arbitrary names are never logged.

## Persisted metadata and current session

Normalized PostgreSQL `node_capabilities`: composite primary key `(NodeId, Name)`, positive Version, 64-character Name, FK to Node. Each hello atomically replaces the snapshot within an EF/PostgreSQL transaction; removed entries disappear. No comma-separated string, accumulation or new pairing.

AppVersion, historical LastSeen and capability replacement share this transaction. The existing brief administrative advisory transaction lock closes disable/re-enable races. A per-Node replacement-chain admission semaphore serializes hello snapshot writes; a superseded lease is cancelled and cannot activate or overwrite the replacement's final snapshot. No heartbeat/resolution holds that semaphore. Capabilities are written on hello/reconnect only, never on each heartbeat. Existing throttled heartbeat-history strategy remains intact.

The current connection lease holds an immutable copy of that session's validated capabilities. Resolver reads `LiveCapabilities` atomically with healthy/ready presence from the process-local Stage 04 registry. Historical capability metadata remains visible while Offline and never makes an Offline Node eligible. An old socket's cleanup cannot remove the new lease. Backend restart clears presence; reconnect reannounces capabilities without replacing identity.

## Resolution and priority

`POST /api/nodes/resolve`, authenticated with existing Node management policy:

```json
{
  "requiredCapabilities": [{ "name": "audio.output", "minimumVersion": 1 }],
  "preferredNodeId": null
}
```

Required list: 1–32 unique known names and positive integer minimum versions; unknown/invalid/duplicate requirements return HTTP400 `invalid_target_requirements`. All requirements use AND. An unknown advertised capability cannot be requested for resolution.

Eligibility:

1. Enabled and not revoked according to administrative metadata.
2. Current ready, unexpired connection lease (not LastSeen age).
3. Every required capability exists in that lease with version >= minimum.
4. Eligible explicit PreferredNodeId wins.
5. Otherwise sort TargetPriority DESC, CreatedAt ASC, Id ASC (C# Guid comparison).

Caller and platform have no implicit preference. An ineligible preference falls back normally. No random/database/dictionary ordering. Global `TargetPriority` defaults to 0, persisted integer range **-1000..1000**, protected both by domain validation and DB constraint. `PATCH /api/nodes/{id}/priority` with `{ "targetPriority": 20 }` uses existing management authorization. This is not capability-specific priority.

HTTP200 result has a public Node summary (`id`, `name`) plus bounded counts (`onlineNodes`, `capabilityCompatibleNodes`). If none is eligible: `node: null`, `code: "no_eligible_node"`. It never chooses an arbitrary Online Node. No credential or unrelated metadata is returned.

This is a momentary selection snapshot, **not a delivery guarantee**: a Node can disconnect immediately after resolution. Future dispatch must revalidate eligibility, lease and administrative state. Process-local presence assumes one API instance; clustering needs an explicit future design.
