## Model and persistence

- `AegisNode`: server-created UUID, editable Name, Android/Windows Platform, Enabled, AppVersion, ProtocolVersion=1, PairedAt, CreatedAt, UpdatedAt, optional RevokedAt. AppVersion records the version at pairing; the About UI separately shows the installed version.
- `NodeCredential`: one per Node; SHA-256 digest, creation and optional revocation dates. No raw permanent credential in this table.
- `NodePairingCode`: digest, public selector, optional issuing Node, expiry, consumption and failed-attempt budget.
- `NodePairingAttempt`: temporary reservation, registration data, credential/recovery-key digests and an encrypted retry receipt. **No Node exists until finalization**.

Migration: `20261003005154_AddNodeIdentityPairing`. Tables: `aegis_nodes`, `node_credentials`, `node_pairing_codes`, `node_pairing_attempts`. Foreign keys, unique code selector/attempt NodeId/code consumption, expiry indexes and constraints cover platforms, protocol, name, 32-byte hashes, failed attempts and revoked-disabled consistency. Existing chat/memory tables are unchanged.

The administrative registry uses transaction-scoped PostgreSQL advisory lock `7070003`, following the existing registry pattern. Every mutation rechecks the actor under that lock; no cached authentication state. PostgreSQL timestamps are normalized to microseconds so replayed establishment responses remain consistent.

Node identity is independent of connections and future metadata. No presence, heartbeat, capabilities or location fields exist.

## Credential and pairing protocol

Permanent credential format:

```text
aegis-node-v1.<server NodeId in N format>.<32 random bytes, base64url without padding>
```

The secret has 256 bits of CSPRNG entropy. A fast SHA-256 digest is appropriate for this randomly generated credential; it is not a human password. Validation uses `CryptographicOperations.FixedTimeEquals`. Neither hashes nor credentials appear in management DTOs.

Pairing codes contain **24 Crockford Base32 characters**, displayed as six groups of four. Total randomness is 120 bits. Eight characters are a public lookup selector; the remaining 16 retain 80 bits of entropy even when that selector is known. Only the selector and full-code digest are stored. Codes expire after ten minutes and are consumed once.

1. Native code creates an AttemptId and 256-bit recovery key and **writes a checkpoint to OS secure storage before contacting the backend**. A failed initial write causes no server registration.
2. `pair` validates and atomically consumes the code, reserves a server NodeId and generates its credential. The pending reservation expires with the code. It cannot authenticate as a Node.
3. Native code saves the credential in the same OS-protected checkpoint. Only then does it call `pair/finalize`.
4. Finalization creates Node + hashed credential atomically and erases the pending retry receipt. A lost finalization response can be retried with the saved credential and returns the existing Node.
5. Native code saves the confirmed identity. Restart resumes incomplete establishment first; a confirmed installation never creates a new Node on startup.

**One logical issuance, with bounded transport replay:** a response lost before durable native credential storage must be recoverable. The temporary receipt is AES-256-GCM encrypted with the native client's recovery key (12-byte nonce, 16-byte authentication tag, AttemptId as AAD). The backend stores only the recovery-key digest, not that encryption key. Exact retries of the same pending attempt can recover the same issued credential until expiry; a different device/attempt cannot reuse the code. This is limited to establishment. No GET or post-establishment API exports the credential. The permanent credential record remains hash-only.

Failed secure writes leave a recoverable checkpoint; a Node is not committed before secure storage confirmation. If backend finalization succeeds but the final local write fails, the earlier secure checkpoint already contains the credential, and restart retries finalization idempotently. Expired unconfirmed attempts create no orphan Nodes. Definitive invalid/expired-code errors clear the temporary checkpoint; network errors preserve it.

Expired material is pruned during successful pairing/code administration or explicit local `cleanup`. There is no cleanup heartbeat/background Node runtime. Material may remain encrypted in an idle database until cleanup, but it cannot be used after expiry.

## Bootstrap and recovery

`backend/tools/Aegis.NodeAdmin` is a separate local executable, shipped alongside the API in the Docker image. It opens the configured database directly and has **no HTTP listener**. It requires server/container/DB administrative access; there is no public bootstrap or admin-code endpoint.

After deploying the Stage 03 backend image, apply migrations (Compose Development also applies them on startup):

```bash
docker compose build aegis-api
docker compose up -d aegis-api
docker compose exec -T aegis-api dotnet node-admin/Aegis.NodeAdmin.dll migrate
docker compose exec -T aegis-api dotnet node-admin/Aegis.NodeAdmin.dll pairing-code
```

The last command prints the code once to the operator's terminal with its UTC expiration. Do not send it to shared application logs, tickets or shell history. In **Dispositivos / Nodes**, enter the device name and code. Bootstrap codes are accepted only within their expiry and consumption budget.

Outside Docker, supply `ConnectionStrings__AegisDatabase` or `AEGIS_DB_CONNECTION_STRING` through the local environment and use:

```bash
dotnet run --project backend/tools/Aegis.NodeAdmin -- migrate
dotnet run --project backend/tools/Aegis.NodeAdmin -- pairing-code
```

An active authenticated Node generates subsequent codes using **Adicionar dispositivo**. The issuing Node must still be active when the code is redeemed and finalized.

If the last Node is disabled, an administrator can recover without editing PostgreSQL:

```bash
docker compose exec -T aegis-api dotnet node-admin/Aegis.NodeAdmin.dll enable <NodeId>
docker compose exec -T aegis-api dotnet node-admin/Aegis.NodeAdmin.dll cleanup
```

A revoked Node can never be re-enabled. Generate a new local bootstrap code and pair a new identity; the old revoked record remains auditable. Losing application data or deleting its OS credential likewise requires new pairing. Do not reinstall/clear application data as an update procedure.

No production API, database or owner's devices were modified by the agent; all backend runtime validation used disposable Docker services/database `aegis_nodes_test`. Production deployment/migration is a prerequisite for using pairing against `https://aegis.phcastello.com`.

## Native storage and WebView boundary

Dependencies: `keyring-core 1.0.0`, `windows-native-keyring-store 1.1.0`, `android-native-keyring-store 1.0.0`; CSPRNG/encoding through `uuid`, `getrandom`, `base64`; existing Reqwest now enables JSON. No new Node storage plugin accessible to JavaScript. The official Rust-only `tauri-plugin-single-instance 2.5.2` is added on Windows to prevent two processes racing over the same installation checkpoint; Android retains its existing singleTask activity.

- **Windows:** Windows Credential Manager generic credential; persistence explicitly **Local**, not roaming Enterprise. Stable service `com.aegis.node.identity.v1`, user `installation`. Native operations are serialized to avoid concurrent access to the same entry. The official single-instance plugin is registered first on Windows; a second launch focuses the existing window and exits before vault initialization. No new frontend plugin permission is needed. [Official plugin documentation](https://v2.tauri.app/plugin/single-instance/). [Library documentation](https://docs.rs/windows-native-keyring-store/latest/windows_native_keyring_store/).
- **Android:** named OS store `aegis-node-identity-v1`; encrypted SharedPreferences contain ciphertext, with AES/GCM protection backed by Android Keystore. Tauri Mobile supplies the NDK context used by the library. Android backup is disabled; no new Android runtime permission is required for this storage. [Library documentation](https://github.com/open-source-cooperative/android-native-keyring-store).

Keep the application/package identifier, store names, entry mapping and release signing identity stable across upgrades. Do not substitute debug APK signing for existing release installations. OS-store unavailability fails closed; it never falls back to JSON, localStorage, IndexedDB or a hardcoded vault password. A corrupt/unavailable Keystore requires OS/app-data recovery and new pairing, not bypassing protection.

The vault checkpoint binds credentials to the normalized backend origin: changing development configuration cannot send an existing identity to a different server. Official builds require HTTPS. HTTP remains an explicit debug-only development option; use HTTPS for real credentials outside isolated tests. Native Reqwest rejects redirects, uses a ten-second timeout and bounds response data to 2 MiB.

Vue receives typed public status and Node DTOs only. Rust sends Node authentication headers and performs pairing/finalization/management. The code entered by the user and a newly generated temporary pairing code are shown in the UI; the permanent credential and recovery key never cross IPC. Revocation replaces the secure entry with a secret-free tombstone. Ordinary network errors retain the credential; disabling retains it for reactivation.

The local main WebView has seven narrowly scoped Node command permissions. The real Windows integration test caught the capability being omitted from the explicit enabled-capabilities list; this was corrected without granting broader permissions, and a configuration regression test now checks the activation and local/main/Android/Windows scope. No generic HTTP, file or credential-store command is exposed. Chat streaming remains on the accepted Stage 02 transport and shared UI; Web Client/PWA, Service Worker and Web Push remain intact.

## Android dependency durability finding and correction

Review found `android-native-keyring-store 1.0.0` calling `SharedPreferences.Editor.commit()` while its callers ignored the returned boolean. Android specifies `false` as a failed persistent write. That violates the secure-storage confirmation requirement: the backend could create a Node whose credential was only present in process memory. This is a wrapper error-propagation defect, not a fundamental Tauri, WebView or Keystore limitation. [Android API contract](https://developer.android.com/reference/android/content/SharedPreferences.Editor#commit()).

Before release, pinned the upstream 1.0.0 source under `apps/aegis-node/src-tauri/vendor/android-native-keyring-store`, preserving MIT/Apache licenses and documenting its archive checksum and exact four-file change in `AEGIS-PATCH.md`. The JNI commit wrapper now converts every false result into a platform failure. Crypto, keystore aliases, encrypted file format and the public credential-store API are unchanged; there is no second storage system or invented cipher.

The native manager also re-commits a pending checkpoint before any pairing request and before every finalization. Readback can see an in-memory update after a failed disk write; it is insufficient as proof of durability. Failure-injection tests model this and prove no pairing/finalization until a later successful write. The exact patched boolean check has two portable tests; a real Android APK compiled and linked the correction. Actual disk-failure/device validation remains **NOT EXECUTED**.

Reasonable alternatives are a verified upstream fixed release or another maintained Keystore backend with equivalent durability/error behavior. The transparent pinned source correction is used until that upstream option exists; remove it only after verifying failure propagation and preserving existing store names. Do not solve this with plaintext, a hardcoded vault password or read-after-write alone. The vendored dependency is an explicit maintenance risk for Stage 04.

## API and administrative semantics

Authentication scheme/header: `Authorization: AegisNode <credential>`. ASP.NET authentication handler and explicit `NodeManagement` policy supply the current NodeId from verified claims. Authentication is checked on every Node request; administrative actions recheck it transactionally. ASP.NET's implicit single-scheme default is explicitly suppressed, so unprotected chat/tool routes do not acquire Node authentication automatically. [ASP.NET behavior documented by Microsoft](https://learn.microsoft.com/en-us/aspnet/core/breaking-changes/7/default-authentication-scheme).

| Endpoint | Authorization | Purpose |
|---|---|---|
| POST `/api/nodes/pair` | Temporary code + native recovery proof | Reserve identity / recover same pending attempt |
| POST `/api/nodes/pair/finalize` | Issued credential + attempt | Confirm durable storage; idempotent finalization |
| GET `/api/nodes` | Active Node | Registry, including disabled/revoked identities |
| GET `/api/nodes/me` | Active Node | Current backend-owned identity/name |
| PATCH `/api/nodes/{id}` | Active Node | Rename |
| POST `/api/nodes/{id}/disable` | Active Node | Reversible disable |
| POST `/api/nodes/{id}/enable` | Active Node | Re-enable a non-revoked identity |
| POST `/api/nodes/{id}/revoke` | Active Node | Permanent credential invalidation |
| POST `/api/nodes/pairing-codes` | Active Node | Pair another installation |

`Enabled=false` causes `403 node_disabled` for Node operations. Another active Node or the local administrator can re-enable it. `RevokedAt!=null` invalidates the credential permanently: correct old credentials receive `401 node_revoked`; wrong/unknown credentials receive generic `401 node_authentication_required` and do not reveal status. Revoked identities cannot be renamed or re-enabled (`409`). No secret is returned by management endpoints.

Self-disable/revoke requires explicit UI confirmation with the local recovery warning. The app recognizes disabled/revoked state on startup or the next requested administrative interaction; no periodic polling/presence is introduced. Chat remains available unpaired, disabled or revoked. The panel provides list, current-device marker, registration metadata, rename, enable/disable, revoke and code generation; Retry is user-driven.

## Threat model and limits

- Public Internet callers cannot create administrative codes or list/manage Nodes. Anonymous pairing only accepts cryptographic, short-lived, one-use proof.
- Five wrong secrets against a known selector invalidate its code. Anonymous pairing/finalization is limited to 20 requests/minute per socket peer IP plus 100/minute globally. Code creation is limited to three/minute per authenticated Node and ten unconsumed codes per issuer.
- Arbitrary `X-Forwarded-For` is not trusted. Behind a reverse proxy, socket-peer quotas can be shared by devices; configure a properly trusted proxy boundary before increasing limits or introducing client-IP forwarding. It is a safety/convenience limitation, not a hidden bypass.
- A leaked database contains permanent/code hashes and transient ciphertext; it does not provide usable credentials, full live codes or receipt decryption keys. High-entropy secrets resist offline guessing. Server/database administrator compromise remains a trusted-boundary compromise.
- Possession of an enabled non-revoked credential authorizes management of this single-owner registry. There is no multi-user administrative RBAC in v1. Protect pairing codes and the local server administration path.
- Node credentials authorize Node operations only. Existing Gmail/Calendar/memory/chat trust boundaries are unchanged and are **not secured merely by introducing Node identity**.
- Application logs contain no pairing codes, credentials, authorization headers or secure-store content. Local CLI output is the intentional one-time administrative disclosure. Do not enable request body/header capture for these routes.
- The local main WebView is trusted to invoke its explicit management commands. Script compromise there could request Node management even though the secret cannot be read; restrictive navigation/CSP and shared Markdown sanitization remain necessary. There is no remote-page capability grant or generic vault command.
- A compromised OS/user account or compromised native process is outside the protection provided by an OS credential store. No invasive hardware identifiers are collected.

## Owner acceptance procedure

1. Deploy the Stage 03 backend/migration; generate the bootstrap code locally. Install the signed next preview over the accepted Stage 02 releases; do not clear app data.
2. Pair **PC Pedro** on Windows. Record the public NodeId. Close/reopen several times; verify one Node and the same NodeId.
3. From PC, choose **Adicionar dispositivo**. Pair physical Android as **Celular Pedro**. Restart/force-close/reopen several times; verify exactly two Nodes. The Android secure-store path must be exercised on the real device.
4. Rename Android to **Pixel** from PC; manually refresh Android and verify the backend-owned name. Disable Pixel: its next Node operation must show Disabled/403. Re-enable from PC; Retry on Android must work with its original identity.
5. Revoke Pixel from PC; Android's next Node operation must show revoked and request new pairing, with no retry loop. Verify the old identity cannot be re-enabled. New pairing creates a different identity; its predecessor remains revoked.
6. Exercise self-disable/recovery with local `enable`, and last-Node revocation/recovery with a new local code. Never edit database secrets manually.
7. On Windows verify the entry in Credential Manager, close/reopen and check retrieval; after revoke confirm the OS entry no longer carries the secret. Inspect ordinary app files for absence of credential plaintext, without exporting the secret to logs. On a debug Android test build, equivalent inspection may use `run-as com.aegis.node`; ciphertext in native private preferences is expected. Release devices generally cannot use `run-as`.
8. At the next natural preview update, record NodeIds before and after a signed A→B update on both devices. The Stage 02 .2→.3 test predates Node identity and **does not establish this new acceptance criterion**.

## Stage 04 risks and explicit deferrals

The pinned Android dependency durability correction must remain covered until upstream resolves it. Physical Android Keystore/lifecycle and paired update preservation still need owner evidence. OS-store/library mapping and application signing identity must remain stable. Single-owner Node management, shared reverse-proxy rate quotas and eventual expired-material cleanup are documented v1 limits. This administrative lock is not a design for future high-frequency transport; Stage 04 must design that workload separately while retaining identity.

No Stage 04+ feature is implemented: heartbeat, persistent sockets, reconnect/presence, availability, background reachability/runtime, command bus, capability registry, target resolution, notifications, FCM, tray/autostart, native reminders, location/Places/geofencing, battery, audio capability registration, wake word, Linux/Apple/headless clients or automation engine. Accepted Stage 02 release/updater infrastructure is reused as requested. Deferred update UX improvements remain backlog.
