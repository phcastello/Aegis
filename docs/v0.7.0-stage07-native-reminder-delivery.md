## Arquitetura

`reminder_create → ReminderService → ReminderWorker → ReminderProcessor →
NodeTargetResolver → notification.show@1 → NodeNotificationDispatcher →
live_websocket ou FCM → notification nativa`.

Service, scheduler, leases de dois minutos, timezone, contexto observado das tools
list/update/cancel e métricas de reminders são preservados. Criação consulta
capability **persistida** `notification.show@1` em pelo menos um Node Enabled,
não Revoked; presença/FCM/VAPID/subscription não são requisitos. Sem destino
possível, retorna `notifications_unavailable` e não cria reminder.

No disparo, o resolver usa capability compatível e Enabled/não Revoked,
reachability (Online ou BackgroundReachable), prioridade decrescente,
CreatedAt crescente e NodeId como desempate determinístico. Não há preferência de
plataforma, NodeId escolhido pelo modelo ou broadcast. Android background com
prioridade 20 ganha de Windows Online com 10; Android sem rota permite Windows.

O dispatcher existente revalida administração, capability e rota antes de envio;
live usa a sessão saudável e FCM usa registration válida. A seleção interna não
exige inventar uma identidade de Node para o worker nem expõe endpoint anônimo.
Title: `Aegis`; Body: texto do reminder. Tocar abre a Aegis pelo comportamento
nativo existente. Sem actions, snooze ou recurrence.

`reminder_delivery_attempts` fica intacta como histórico legado, sem mapeamento

aceite Web Push anterior ou ACK, evitando replay de broadcasts parcialmente
aceitos. Processing sem aceite volta a Scheduled; leases antigas são liberadas.

não são reabertos. Fazer downgrade após envios nativos pode perder a auditoria
nativa; guardar backup e preferir correção adiante.

## Retry e idempotência

Aceite técnico: `success`, `accepted` ou `duplicate`, levando a Triggered.
`accepted` indica aceite FCM, não confirmação de display físico. Pending no
servidor retorna `busy`, nunca `duplicate` sem confirmação do Node.

Até cinco tentativas, com atrasos 10s, 30s, 2m e 5m; ausência de Node também
consome o orçamento. Reaparecimento dentro da janela permite entrega. Esgotamento
leva a Failed. Polling mantém `AEGIS_REMINDER_POLL_SECONDS` (default 5), agora
em ReminderOptions, separado de WebPushOptions.

Tentativa e comando são persistidos antes da rede. Outcome interrompido vira
`outcome_unknown`; timeout/erro possivelmente posterior ao envio é conservador.
Retries ambíguos reutilizam **NodeId, CommandId e expiração originais**, inclusive
com DbContext novo/restart. Não migram para outro Node enquanto o primeiro envio
pode ter ocorrido. Resultado negativo antes de envio permite resolver novamente.
O dedupe nativo do Stage 06 reconhece o command repetido.

TTL do command é 300s, limite do contrato Stage 06, sem renovação em replay
ambíguo. Se expirar sem confirmação, termina Failed em vez de recriar um command
potencialmente duplicado. Isso pode encurtar retries de outcomes desconhecidos;
indisponibilidade sem envio mantém a janela normal inteira. Não promete exactly-once
frente a falha do armazenamento local do Node, nem adiciona fila infinita.

Locks/transações só cobrem claim e bookkeeping. Rede ocorre fora deles;
lease e ACK são rechecados antes de dispatch. Resultado de worker antigo não
sobrescreve tentativa já reconciliada por outro worker. Métricas de criação,
trigger/delay/cancel/update/failure continuam; entrega tem contadores próprios
`aegis_reminder_delivery_{attempts,accepted,failed}_total` e os do dispatcher.

## Web Push legado

ReminderService, ReminderProcessor e ReminderWorker não usam IWebPushClient,
PushSubscription ou tokens Web Push. Infraestrutura PWA/VAPID/endpoints/tokens e
histórico permanecem como compatibilidade/dívida para cleanup posterior. Registro
Web Push sozinho não libera reminder_create. Nenhuma nova entrega de reminder
passa por Web Push.
