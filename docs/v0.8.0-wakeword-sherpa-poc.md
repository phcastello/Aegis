## Pronúncia e arquivo de keywords

O `en.phone` distribuído representa **AEGIS como `IY1 JH AH0 S`**. Essa leitura
inglesa não foi adotada automaticamente. O comando documentado
`text2token --tokens-type phone+ppinyin --tokens tokens.txt --lexicon en.phone`
consulta esse léxico; escrever AEGIS não estabelece a pronúncia do proprietário.

Antes da confirmação textual, foi avaliada a aproximação inicial
`EH1 ZH IY0 S @Aegis` (“é-jis”). Ela falhou em todos os arquivos e permanece
registrada como tentativa **anterior ao esclarecimento**, não como a pronúncia
confirmada. Uma hipótese com `EY1` foi descartada **sem teste**.

O proprietário informou **“Aéjis”**. Interpretamos a indicação como “a-é-jis”,
aproximadamente `/aˈɛʒis/`, e fixamos:

```text
AA0 EH1 ZH IY0 S @Aegis
```

Todos os símbolos existem no vocabulário do modelo. Os IDs são `AA0=3`,
`EH1=26`, `ZH=71`, `IY0=40`, `S=57`. O sufixo de stress faz parte do token.
`AA0` aproxima o “a” aberto inicial átono; `EH1` a vogal “é” tônica; `ZH` o
“j”; `IY0` a vogal final átona; `S` a fricativa final. Fonemas CMU ingleses
aproximam sons portugueses, sem equivalência acústica garantida: em particular,
`AA0` é mais posterior que o `/a/` português. A indicação escrita esclarece a
intenção, mas não constitui transcrição fonética auditada.

As sequências válidas são escritas diretamente no arquivo de keywords,
mantendo o rótulo lógico único **Aegis**, sem acrescentar Hey, Ei ou outra
palavra. Não houve G2P improvisado, STT substituindo KWS ou treinamento.
[`sherpa-keywords.json`](../scripts/wakeword-poc/sherpa-keywords.json) registra
as duas representações efetivamente usadas e suas limitações.

## Configurações e execução

Foram executados **três lotes de 37 arquivos: 111 avaliações**, mantendo a
mesma divisão 23/8/6. São replays dos mesmos dados, não 111 amostras distintas.

| ID no CSV | Fonemas | Boosting score | Trigger threshold | Papel |
| --- | --- | ---: | ---: | --- |
| `default` | `EH1 ZH IY0 S` | 1,0 | 0,25 | tentativa preliminar antes de “Aéjis” |
| `confirmed-default` | `AA0 EH1 ZH IY0 S` | 1,0 | 0,25 | padrão para a pronúncia esclarecida |
| `confirmed-sensitive` | `AA0 EH1 ZH IY0 S` | 2,0 | 0,15 | último ajuste de sensibilidade |

Os dois primeiros lotes usaram os valores padrão documentados de score e
threshold. O último aumentou boosting e reduziu threshold moderadamente,
após ausência completa de detecções; como ambos mudaram, não isola o efeito
causal de cada parâmetro. Nenhum ajuste adicional foi executado.

Demais parâmetros constantes: CPU, **uma thread explícita** (a API Python
tem default de duas), sample rate 16.000, feature dim 80, max active paths 4,
trailing blanks 1. O PCM foi apenas convertido de int16 para float32 dividindo
por 32768, conforme o exemplo oficial. Um stream novo por arquivo, reset
imediato após ativação e cauda de 0,66 s de zeros para flush, seguindo o
[exemplo Python](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/python-api-examples/keyword-spotter.py).
Não houve VAD, normalização adicional ou silêncio removido.

**Android:** existem bindings Kotlin/JNI oficiais, distribuição ARM64 e
[exemplo KWS com AudioRecord](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/android/SherpaOnnxKws/app/src/main/java/com/k2fsa/sherpa/onnx/MainActivity.kt),
PCM mono 16 kHz/16 bits convertido para FloatArray. `OnlineStream.acceptWaveform`
permite alimentar PCM continuamente; o binding carrega `sherpa-onnx-jni`.
O AAR oficial multi-ABI tem aproximadamente 49,4 MB comprimidos: não é o
incremento final do APK ARM64. O exemplo é uma Activity; não comprova escuta
com tela bloqueada. Nenhum build/JNI ou teste Android foi feito nesta tarefa.

**Windows:** há C API e
[wrapper/exemplo Rust oficial de KWS](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/rust-api-examples/examples/keyword_spotter.rs)
com entrada PCM, decode, resultado e reset. Usá-lo num worker do Node Tauri é
uma possibilidade de engenharia, não integração comprovada. Dependências
nativas incluem ONNX Runtime e runtime C/C++; distribuição estática ou shared
exige escolher o empacotamento das bibliotecas.

Como referência de tamanho **Linux**, foram medidos ONNX Runtime 27.026.609
bytes, C API 4.892.512 bytes, C++ API 266.872 bytes e binding Python 5.922.273
bytes. Python/ALSA do pacote experimental não precisam ser levados ao Node;
isso não estima o pacote final Windows/Android. CPU provider dispensa GPU.
O suporte nativo documentado é adequado ao tipo de integração pretendido,
mas a ausência de reconhecimento impede recomendá-la com este modelo.

## Reprodução e artefatos

Dependências/modelos permanecem em
`/home/phc/.cache/aegis-wakeword-poc/sherpa`; áudios continuam no `data/`
existente. Logs de controle, eventos, manifests, keywords e resumos são
privados. Apenas scripts, metadados fonéticos e métricas entram no Git.

```bash
bash scripts/wakeword-poc/install-sherpa.sh
sherpa_root="$HOME/.cache/aegis-wakeword-poc/sherpa"
sherpa_python="$sherpa_root/venv/bin/python"
sherpa_model="$sherpa_root/sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20"

# Use destinos novos: os scripts não sobrescrevem resultados.
"$sherpa_python" scripts/wakeword-poc/check-sherpa.py \
  --model "$sherpa_model" --output "$sherpa_root/control-repeat"

"$sherpa_python" scripts/wakeword-poc/sherpa.py \
  --data "$HOME/.cache/aegis-wakeword-poc/data" --model "$sherpa_model" \
  --variant confirmed --config confirmed-default \
  --output "$sherpa_root/confirmed-default-repeat"

"$sherpa_python" scripts/wakeword-poc/sherpa.py \
  --data "$HOME/.cache/aegis-wakeword-poc/data" --model "$sherpa_model" \
  --variant confirmed --config confirmed-sensitive --score 2 --threshold 0.15 \
  --output "$sherpa_root/confirmed-sensitive-repeat"
```

Para reproduzir estritamente a tentativa anterior ao esclarecimento, usar
`--variant primary --config default` em outro destino. Ela não é recomendada
para representar “Aéjis”. O instalador fixa versões e hashes dos wheels/tar,
recusa destinos em checkout Git e baixa somente dependências e modelo públicos.
`sherpa.py` reutiliza `load_data` da infraestrutura anterior apenas para checar
integridade; importar esse helper **não executa Rustpotter**.

Timestamps dos tokens podem reiniciar após resets internos, e o binding não
expõe o offset `start_time`. `emission_timestamps` registra a posição absoluta
de PCM já alimentado, em blocos de 100 ms, não latência. Essa ressalva permanece
no CSV e no runner, embora não tenha ocorrido evento privado neste experimento.

Verificações: integridade ZIP/originais/WAVs; baseline Git inalterado;
instalação pinada e idempotente; dois exemplos oficiais com tokens/timestamps
em lote e no runner incremental; 111 testes privados; conferência de CSV,
splits e métricas; `py_compile`, `bash -n`, `git diff --check` e recusa de
destinos dentro do checkout. Não houve alteração de dependências da Aegis,
reconversão, deploy, migration, publicação, PR, merge ou implementação nativa.

## Conclusão e próximo passo

**NO-GO para este modelo zh/en, com esta palavra e estas configurações.** Não
há configuração mais promissora entre as testadas: todas rejeitam tudo. A
representação confirmada com parâmetros padrão é a referência mais simples
para reproduzir o problema; aumentar sensibilidade não produziu benefício.

O controle positivo oficial, a validade dos tokens e a confirmação da entrada
PCM tornam uma instalação quebrada ou erro básico de alimentação hipóteses
menos prováveis. A limitação mais consistente é **cobertura acústica/fonética
insuficiente para a pronúncia portuguesa em um modelo chinês/inglês**, junto
da aproximação entre os inventários fonéticos. Isso é inferência; o experimento
não separa erro de aproximação fonética de limitação do modelo, nem reprova
todo o runtime sherpa-onnx.

O próximo passo econômico é **encerrar o tuning deste modelo e não construir
integração Android/Windows com ele**. Uma eventual continuação deve começar
pela disponibilidade de um modelo KWS pré-treinado que cubra português, antes
de investir em outro benchmark ou hardware. Não foi iniciada uma terceira
biblioteca, ASR completo, classificador próprio ou treinamento personalizado.
