# v0.7.0 — Stage 01: Tauri Foundation

Status: **implementação da fundação; aceite nativo pendente**. O Stage só pode ser declarado concluído após as validações Windows e Android físico abaixo. Os testes portáveis não substituem testes de WebView, IPC, instalação ou ciclo de vida.

Branch: `feat/v0.7.0-stage01-tauri-foundation`, criada a partir de `origin/main` (`1397934`). A branch local `main` não foi alterada. A versão do backend/PWA nessa base é v0.6.0; alterações de outras branches não foram incorporadas.

## Escopo e arquitetura

Foi criada uma aplicação independente em `apps/aegis-node/`, usando o scaffold oficial `create-tauri-app` 4.7.4 (`vue-ts`). O backend ASP.NET Core/.NET 8 mantém suas camadas Api, Application, Domain e Infrastructure, persistência PostgreSQL e integrações atuais. O PWA Vue existente continua em `frontend/aegis-pwa/`, com seu Service Worker e Web Push. Nenhum código desses dois produtos foi alterado.

A nova aplicação mostra Aegis, Platform, Backend e Retry. Ao montar a tela, consulta o runtime e o backend. Retry desabilita consultas concorrentes, remove um resultado Connected antigo enquanto verifica e permite recuperação após falha. Não há polling, heartbeat ou serviço de background.

```text
Vue DiagnosticsPanel
    → useDiagnostics (estado e apresentação)
    → services/runtime (dois comandos IPC sem argumentos)
    → Rust platform/config/health
    → GET <origem configurada>/api/health
```

A identificação usa `cfg!(target_os)` no Rust e retorna `android` ou `windows`. Outros alvos retornam `unsupported`; isso não configura suporte a Linux, iOS ou macOS. Não há detecção por User-Agent nem entidade Node.

O endpoint existente está em `backend/src/Aegis.Api/Controllers/HealthController.cs`: `GET /api/health`, HTTP 200 com `{"status":"ok"}`. O cliente exige HTTP 2xx e o contrato JSON esperado. Uma página de proxy, JSON inválido, status diferente, falha HTTP, falha de transporte ou timeout resulta em Unavailable. Connected indica disponibilidade desse endpoint; **não verifica banco, modelos ou integrações**, pois esse endpoint não os verifica.

## Configuração do backend

Crie `apps/aegis-node/.env.local` copiando o exemplo do próprio app. A variável é **AEGIS_NODE_API_BASE_URL**, lida por `build.rs` e compilada no binário Rust. Uma variável do shell/CI tem precedência sobre `.env.local`. O `.env` da raiz não é lido. Valores ausentes ou inválidos são exibidos como Unavailable com explicação; não há fallback silencioso para localhost.

Windows debug, quando o backend roda no próprio computador:

```dotenv
AEGIS_NODE_API_BASE_URL=http://localhost:8090
```

Android físico, usando um nome LAN que o telefone consiga resolver:

```dotenv
AEGIS_NODE_API_BASE_URL=http://backend.lan:8090
```

`backend.lan` é um exemplo, não um serviço provisionado. Substitua pelo hostname/IP real do servidor acessível pelo telefone. Não versione esse valor. Em release:

```dotenv
AEGIS_NODE_API_BASE_URL=https://backend.example
```

`backend.example` também deve ser substituído por uma origem real. A configuração aceita apenas uma origem HTTP/HTTPS absoluta, sem `/api`, caminho adicional, credenciais, query ou fragmento. Normaliza espaços externos e a barra final da origem. Rejeita bind addresses como `0.0.0.0` e loopback no Android, explicando que localhost pertence ao próprio dispositivo. Não reescreve para `10.0.2.2`, não usa `adb reverse` e não instala proxy oculto.

A URL é configuração **de build**, inclusive no modo dev. Após alterá-la, reinicie `tauri dev` ou gere novo build/APK; Retry refaz a consulta, não altera a URL. Cargo acompanha alterações de `.env.local` e da variável de ambiente. Uma distribuição futura para outro backend requer outro build neste Stage.

### Backend local/LAN e Android físico

O Compose existente publica a API em `8090` (`ASPNETCORE_URLS=http://+:8090`) e o PWA em `5173`. O telefone precisa estar numa rede que alcance esse servidor, com DNS correto, sem isolamento Wi-Fi e com acesso permitido à porta escolhida. Quando a API é executada fora do Docker, o launch profile atual usa localhost; para testes LAN use explicitamente:

```powershell
dotnet run --project backend/src/Aegis.Api/Aegis.Api.csproj --no-launch-profile --urls http://0.0.0.0:8090
```

Mantenha o ambiente e a configuração de banco requeridos pelo backend. `0.0.0.0` é endereço de bind do **servidor**, nunca URL do app. Verifique `http://<servidor-LAN>:8090/api/health` a partir do telefone antes do teste nativo. Faça testes HTTP somente em rede local confiável. Builds debug permitem esse diagnóstico; builds release exigem HTTPS. Não abra todas as portas do firewall e não exponha a API de desenvolvimento à Internet para contornar conectividade.

HTTP acontece no Rust, não via fetch na WebView. Por isso os origins Tauri não foram acrescentados ao CORS do backend. Não há permissão de HTTP genérico exposta ao JavaScript. Certificados TLS continuam verificados; certificados autoassinados sem cadeia confiável resultam em Unavailable. Neste Stage o cliente Rustls usa as raízes públicas WebPKI, sem mecanismo de CA personalizado.

## Segurança

A capability `diagnostics` vale apenas para a janela local `main` nos alvos Android/Windows. Permite somente `allow-runtime-info` e `allow-check-backend`. Não usa `core:default`, wildcard de janela, remote origins, filesystem, shell, opener ou plugin-http. `AppManifest::commands` inclui os comandos no controle ACL; registrar comandos no invoke_handler sozinho não garantiria essa restrição.

O comando de health não aceita URL, headers ou método vindos da WebView. Usa somente a origem compilada, GET `/api/health`, timeout total de cinco segundos, resposta limitada a 4 KiB e redirects desabilitados. Não armazena tokens nem mostra corpos de erro remotos.

A CSP de build restringe recursos aos assets locais e IPC, bloqueando frames, objetos e envio de formulários. A CSP de dev permite também WebSocket para HMR e estilos inline do Vite. Ela não concede IPC a páginas remotas. O dev server deve ser usado em uma rede confiável.

O Android mantém o manifest oficial: permissão INTERNET, sem localização, microfone, notificações ou permissões de serviço. A configuração padrão permite cleartext no debug para Vite/LAN e o desabilita no release; a política Rust também rejeita URL HTTP em release. Não há bypass de TLS nem exceção silenciosa de produção.

## Windows: execução e build

Em Windows, instale Node 22.12+ (ou 24 LTS), Rust 1.94+, Visual Studio Build Tools com Desktop development with C++/SDK Windows e Microsoft Edge WebView2. Use o toolchain MSVC, seguindo os [pré-requisitos oficiais do Tauri](https://v2.tauri.app/start/prerequisites/).

```powershell
rustup default stable-msvc
rustup target add x86_64-pc-windows-msvc
cd apps/aegis-node
npm ci
Copy-Item .env.example .env.local
# Edite .env.local antes de executar.
npm run check
npm test
npm run check:rust
npm run test:rust
npm run dev:desktop
```

`dev:desktop` executa `tauri dev --target x86_64-pc-windows-msvc`. Não acrescenta tray, autostart ou execução persistente.

Para build distribuível, configure uma URL HTTPS real (release rejeita HTTP) e execute:

```powershell
npm run build:desktop
```

O comando usa `tauri build --target x86_64-pc-windows-msvc`; produz executável e instalador NSIS sob `src-tauri/target/x86_64-pc-windows-msvc/release/`, com instalador em `bundle/nsis/`. Para validar um build debug com backend HTTP LAN, use `npm run build:desktop -- --debug`. Instale/abra o artefato final e repita o roteiro de aceite. Este Stage não adiciona assinatura Windows.

## Android: inicialização, execução e APK

Instale Android Studio, JDK 17 compatível com Gradle, SDK Platform 37.0, Build-Tools 37.0.0, Platform-Tools, Command-line Tools e NDK 29.0.14206865. Configure JAVA_HOME, ANDROID_HOME e NDK_HOME para os diretórios locais de instalação; esses paths não pertencem ao repositório. Use o [fluxo mobile oficial](https://v2.tauri.app/start/prerequisites/#configure-for-mobile-targets).

```powershell
rustup target add aarch64-linux-android armv7-linux-androideabi i686-linux-android x86_64-linux-android
cd apps/aegis-node
npm ci
Copy-Item .env.example .env.local
# Edite a URL para o backend acessível pelo Android físico.
npm run android:init
adb devices -l
npm run dev:android
```

O projeto já foi inicializado e versionado em `src-tauri/gen/android/`. `android:init` prepara a integração local do toolchain; o CLI gera suas referências locais durante o fluxo. Não versione local.properties, referências absolutas ao registry Cargo, keystores ou outputs gerados. Revise mudanças do init antes de commitar; não sobrescreva ajustes versionados do wrapper. O SHA-256 oficial da distribuição Gradle está no wrapper.

Conecte o telefone por USB, habilite Developer options/USB debugging e autorize o computador. `adb devices -l` deve indicar `device`. O CLI permite selecionar o dispositivo. A configuração Vite usa TAURI_DEV_HOST fornecido pelo CLI, porta fixa 1420 e HMR 1421; a URL do servidor Vite e a URL do backend são configurações diferentes. Verifique que o telefone consegue alcançar ambas no modo dev. O APK com assets empacotados dispensa Vite.

Para gerar APK debug ARM64, destinado a um Android físico moderno:

```powershell
npm run build:android
```

Equivale a `tauri android build --debug --apk --target aarch64`. Artefato esperado: `src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk`. Instalação:

```powershell
adb install -r src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
adb shell am start -n com.aegis.node/.MainActivity
```

Para um dispositivo de outra ABI, use `npm run tauri -- android build --debug --apk --target <alvo>` conforme `npm run tauri -- android build --help`. Embora o diretório de saída se chame `universal`, este comando foi verificado com somente `arm64-v8a`; ele não produz um APK com todas as ABIs. `npm run tauri -- android build --apk --target aarch64` gera release com URL HTTPS; distribuição release, keystore e publicação ainda não foram validadas.

### Artefato gerado

O pacote identifica `com.aegis.node`, versão `0.7.0-stage01` (versionCode 7000), minSdk 24, targetSdk 37 e ABI `arm64-v8a`. Inclui o Vue no binário Rust e não depende de Vite para abrir.

O build final usa uma `.env.local` ignorada, preparada com a origem pública HTTPS já configurada na Aegis. Essa origem respondeu ao health real também via reqwest/Rustls; o valor pessoal não foi versionado. A instalação/runtime Android continua não executada. Para reproduzir em outra máquina, configure a própria URL e gere outro APK. Os builds intermediários com a origem de exemplo foram substituídos pelo build final.

### Roteiro para aceite nativo

Em Windows, execute dev e o artefato instalado, confirme Vue, Platform: Windows e Backend: Connected com a origem configurada. Em um backend de teste que possa ser interrompido, pare a API, pressione Retry e confirme Unavailable; inicie novamente, pressione Retry e confirme Connected. Não pare uma instância compartilhada de produção para esse teste.

Em Android físico, instale o APK configurado para o backend alcançável pelo telefone. Confirme Vue, Platform: Android e Connected. Repita offline/recovery com Retry. Pressione Home, aguarde, abra o app novamente pelo launcher/recentes e confirme que a tela e Retry continuam funcionais. Repita com uma requisição em andamento antes de colocar em background. Uma eventual recriação da Activity deve voltar à tela e realizar a consulta inicial; não há persistência de diagnóstico nem garantia de execução enquanto suspenso.

### Impedimentos encontrados

O build Windows foi tentado de verdade, mas falhou antes de gerar o executável, por ausência de MSVC/lib.exe no host Linux. Isso é uma limitação do ambiente de build, não evidência de falha arquitetural do Tauri/WebView2. A alternativa adequada para este Stage é validar no Windows com os pré-requisitos oficiais, ou gerar o artefato em CI Windows e executar no Windows. Não foi introduzido cross-compiling customizado ou linker alternativo para mascarar esse requisito.

Android: `adb devices -l` retornou lista vazia. Sem hardware físico ou emulador utilizável, instalação, IPC na WebView Android e background → foreground não podem ser atestados. Nenhum resultado físico foi inventado.

## Limitações e riscos para os próximos Stages

- A fundação ainda não prova aceite funcional nas duas plataformas; não liberar o Stage 02 como se esses checks já estivessem concluídos.
- Configuração de URL é de build. Seleção/alteração de servidor em runtime, credenciais e pairing não foram antecipados.
- A probe existente é de disponibilidade HTTP, não readiness de toda a Aegis.
- Certificados, reachability LAN, políticas Wi-Fi e versões reais de WebView precisam ser exercitados nos alvos.
- Recriação/suspensão Android precisa de validação física. Este Stage não promete tarefas de background ou continuidade de requests enquanto o SO suspende o app.
- Stage 02 precisará validar as chamadas reais e streaming/paridade do cliente; sucesso de GET /api/health não prova chat, STT/TTS ou integrações.
- APK padrão é debug/ARM64. Assinatura/distribuição release Android e assinatura Windows não foram configuradas; os ícones ainda são os do scaffold.
- O backend atual mantém seus contratos e acesso existentes; este Stage não acrescenta autenticação de dispositivo nem um modelo de segurança de Nodes.

Nenhuma feature posterior foi implementada: sem entidade/tabelas Node, pairing, autenticação de dispositivo, heartbeat, capabilities de Node, target resolution, socket permanente, online/offline de dispositivos, tray/autostart, notificações nativas/FCM, reminders, recorrência/snooze, Place/GPS/geofencing, wake word, automations, runtime de background, serviços Android ou headless node. As capabilities mencionadas nesta documentação são exclusivamente o mecanismo de permissões Tauri 2.
